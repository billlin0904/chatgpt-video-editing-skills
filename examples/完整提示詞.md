不要用 `$repo/.git` 是否為目錄來判斷 Repo，因為 linked worktree 的 `.git` 是檔案。對每個適用的既有路徑執行以下檢查；video-use 一律適用，HyperFrames 只在我明確要求時適用：

```sh
inspect_repo() {
  repo=$1
  expected_origin=$2
  if [ ! -e "$repo" ] && [ ! -L "$repo" ]; then
    printf '%s\n' "missing repository: $repo"
    return 2
  fi
  inside=$(git -C "$repo" rev-parse --is-inside-work-tree 2>/dev/null) || return 1
  [ "$inside" = true ] || return 1
  commit=$(git -C "$repo" rev-parse --verify HEAD) || return 1
  branch=$(git -C "$repo" branch --show-current) || return 1
  [ -n "$branch" ] || branch="(detached at $commit)"
  actual_origin=$(git -C "$repo" remote get-url origin) || return 1
  [ "$actual_origin" = "$expected_origin" ] || {
    printf '%s\n' "STOP: unexpected origin for $repo: $actual_origin" >&2
    return 1
  }
  status=$(git -C "$repo" status --short) || return 1
  printf '%s\n' "repo=$repo" "origin=$actual_origin" \
    "branch=$branch" "commit=$commit" "status=${status:-clean}"
  [ -z "$status" ] || return 1
}
```

既有路徑若不是 Git worktree、沒有 origin、origin 不精確相符、commit 無效，或 `git status --short` 不為空，都是 hard stop。立即停止對該 Repo 的 pull、reset、覆寫、重新 Clone、依賴安裝、Skill 註冊或其他修改；回報路徑與證據，等我決定安全處理方式。即使 Repo 很乾淨，錯誤 origin 也不能繼續，更不能自動改成官方 URL。

在 Clone 或更新 Repo、安裝套件、使用套件管理器、下載字體檔、下載大型依賴、建立／更改 symlink、改動 Agent Skills 目錄，或建立／修改憑證檔前，先列出每一項預計變更、位置與理由，等待我明確核准。環境檢查本身不代表我已同意後續變更。核准等待期間 Git 狀態可能改變，因此每次依賴安裝或 Skill 註冊前，都要重跑適用的 `inspect_repo`，重新確認 exact origin、branch／commit 與乾淨狀態。

## 階段三｜安裝字幕字體（思源黑體 TW）

官方 Repo：<https://github.com/adobe-fonts/source-han-sans>（SIL Open Font License 1.1）

繁體中文字幕燒錄預設使用思源黑體 TW（Source Han Sans TW）；缺少合適的 CJK 字體時，燒錄結果可能出現豆腐字或退回不合適的系統字體。只接受官方 Repo 的 `release` 分支作為下載來源，不可使用鏡像站、字體整理站或名稱相似的 Repo，也不可默默改用其他字體。

若階段一檢查已確認兩個字重都是一般檔案，回報已存在並跳過本階段；不可重新下載或覆寫既有字體檔。若字體路徑存在但是 symlink、資料夾或其他非一般檔案，停止並回報，不可取代。

缺少字重時，先把下載列為待核准項目（每個字重約 6 MB，預設兩個字重）。核准後執行：

```sh
case "$(uname -s)" in
  Darwin) font_dir="$HOME/Library/Fonts" ;;
  Linux) font_dir="$HOME/.local/share/fonts" ;;
  *) printf '%s\n' 'STOP: unsupported platform; install the font manually.' >&2; exit 1 ;;
esac
font_source=https://github.com/adobe-fonts/source-han-sans/raw/release/SubsetOTF/TW
mkdir -p "$font_dir"
for weight in Regular Bold; do
  font_file="$font_dir/SourceHanSansTW-$weight.otf"
  if [ -e "$font_file" ] || [ -L "$font_file" ]; then
    printf '%s\n' "skip existing path: $font_file"
    continue
  fi
  curl -fL --proto '=https' -o "$font_file" \
    "$font_source/SourceHanSansTW-$weight.otf"
done
if [ "$(uname -s)" = Linux ]; then
  command -v fc-cache >/dev/null 2>&1 && fc-cache -f "$font_dir"
fi
```

回報安裝完成前，必須驗證每個檔案是真正的 OpenType/CFF 字體，`SourceHanSansTW-Regular.otf` 與 `SourceHanSansTW-Bold.otf` 都要以 `OTTO` magic bytes 開頭：

```sh
for weight in Regular Bold; do
  font_file="$font_dir/SourceHanSansTW-$weight.otf"
  [ -f "$font_file" ] && [ ! -L "$font_file" ] || exit 1
  magic=$(head -c 4 "$font_file" | od -An -tx1 | tr -d ' \n') || exit 1
  [ "$magic" = 4f54544f ] || {
    printf '%s\n' "STOP: not a valid OpenType font: $font_file" >&2
    exit 1
  }
done
```

下載失敗或驗證停止時，不可自動刪除任何檔案；回報精確路徑與證據，等我決定。若我需要其他字重、其他地區子集、Super OTC 或可變字型，另列核准項目，並依上游官方 `SourceHanSansReadMe.pdf` 的 Configurations 說明選擇。

## 階段七｜正式執行短影音八大步驟

所有新產物放在原始影片同層的 `edit/`；不可覆寫、搬移、重新命名或刪除原始影片。若 `edit/project.md` 已存在，先讀取並記錄本次工作階段。

### 第一步｜素材檢查

使用 ffprobe 檢查每個來源的影片／音訊 streams、長度、方向、解析度、幀率、旋轉資訊、取樣率、色彩標籤，以及完整可解碼性。確認正確來源與 9:16 目標後，才建立相鄰的 `edit/` 工作區。

### 第二步｜逐字轉寫

在取得本次檔案上傳同意後，使用 PureText Agent API 作為主要且預設路徑，產生逐字原文與 word-level timestamps。轉寫結果依未變更的來源做快取；來源沒變就不要重跑。

若 PureText 無法使用，先交回環境設定流程。如果我拒絕雲端上傳或無法使用 PureText，不能默默切換；先清楚說明本機 Whisper 是時間碼信心較低的降級方案，詢問我是否明確選用。只有我同意後才能使用，並把逐字稿標記為 lower-confidence，對 `edl.json` 每個剪接邊界加做來源播放檢查；不得把它說成與已驗證的 PureText word-level 時間碼同等精準。

人名、書名、工具名、日期、數字與專有名詞無法可靠確認時，列為待確認，不要猜測。

### 第三步｜內容整理

建立可閱讀的校正版逐字稿，找出故事、最強 Hook、核心訊息、單一內容主線、明顯 NG、重複、贅詞、過長停頓、未兌現承諾、可能長度與需要看畫面確認的歧義。這一步只是分析，不是已核准的剪接清單。不可扭曲原意、時間順序或因果關係。

### 第四步｜剪輯決策

在真正決定剪接點前，先用 4～8 句白話向我說明：觀眾看完得到什麼、開頭使用哪一句、核心主線、選用與刪除內容、是否重排、預計長度、視覺方向、字幕方式，以及是否提議圖卡、B-roll、動畫、配樂、音效或 CTA。

等待我明確核准策略。未經核准，不可決定剪接點，也不可自行加入 B-roll、動畫、音效、音樂、CTA 或發布排程。

### 第五步｜逐段粗剪

策略核准後，以 word-aligned kept ranges 建立 `edl.json`。每個範圍保留來源、start、end、beat、quote 與 reason，並保持來源區間和輸出 offset 一致。

- 不可切進字詞內或切掉字頭、字尾。
- 依口語節奏在完整字詞邊界外保留 30–200ms。
- 每個保留段落獨立擷取、處理與驗證，再接合。
- 每段音訊邊界加入約 30ms 淡入淡出，避免爆音或生硬切點。
- 歧義剪接要先查看來源時間軸再決定。

調色或 HLG-to-Rec.709 校正只在技術上確實需要，或我已明確核准時執行；不得把未要求的風格調色說成必要修正。

### 第六步｜轉色／圖卡／字幕

只執行已核准的色彩、圖卡與動畫方案。簡單標題與資訊卡使用 Pillow 靜態圖片；只有已核准的策略需要 HTML、CSS 或 GSAP 動畫，而且環境已 ready 時，才使用 HyperFrames。保留每個動畫的可編輯來源與輸出。

依 EDL 的輸出時間軸生成 `master.srt`：`output_time = word.start - segment_start + segment_offset`。字幕燒錄預設使用已安裝的思源黑體 TW；若字體缺少或驗證失敗，停在安全位置交回環境設定流程，不可默默改用其他字體。字幕在所有畫面與圖卡完成後最後合成，並避開人物臉部與平台 UI 安全區。

### 第七步｜混音與完整預覽

保留清楚自然的人聲，只加入已核准的音樂與效果。處理剪接點音訊銜接、必要的降噪與混音後，輸出一支包含全部核准畫面、字幕與聲音的完整 720p 預覽。

檢查實際渲染出的預覽，不只看來源或時間軸：逐一檢查每個剪接點前後 ±1.5 秒的跳畫面、閃幀、爆音、同步、字幕與疊圖；另查片頭、片尾、中段代表畫面、字幕安全區、色彩、混音、streams、長度、尺寸與完整解碼。只有證據指出明確問題時才能自動修正，最多三輪；超過就停止並回報剩餘問題。

完成預覽 QA 後，把完整 720p 預覽交給我審核，等待我明確核准。此時不得把預覽說成正式定稿，也不得先輸出或交付正式檔。

### 第八步｜QA 與正式定稿

只有我明確核准 720p 預覽後，才渲染一支 1080×1920 的正式 `final.mp4`。

正式檔渲染完成後，必須針對這個正式檔本身重新檢查所有剪接邊界與代表畫面，並執行完整解碼；記錄 streams、長度、尺寸、同步、字幕、色彩與混音。只有正式檔的這些檢查全部通過後，才能交付。順序必須是：預覽 QA → 我核准預覽 → 渲染正式檔 → 驗證正式檔 → 交付。
